# Reviewer boundary — Ticket 04

**Versions:** current prompt `review-prompt-v3`, provider response schema `review-schema-v3`, flag policy `all-valid-changes-v1`. The weaker v1 paid pilot produced invented groups and overlong reasons. V2 added a provider enum and shorter-reason instruction; v3 clarifies processor/funder, NSF, and legal-signal distinctions observed in the batch pilot. V3 keeps the provider-level reason/confidence shape permissive so one malformed item cannot discard a whole batch; the strict application-level proposal schema and per-item validation below are unchanged. These are project choices implementing [Fundo's reviewer request](../CHALLENGE.md#1-the-reviewer), not deployed Fundo policy. The model/prompt remains **provisional** until final quality review in Ticket 07.

`build_request()` takes an accepted transaction **and its existing legacy label**. It creates a sanitized provider request with transaction ID, date, exact signed amount, `name`, optional `merchant_name`/category, legacy group/business-personal flag, matched-rule trace, and ruleset version. It never copies the raw record, synthetic scenario, ground truth, revenue answer, features, or offer. Fixed system instructions are separate from the JSON-serialized user data. Bank descriptions are counterparty-controlled **data**, not instructions; the provider is given no tools. The synthetic `IGNORE PRIOR INSTRUCTIONS...` case tests the serialization boundary and a fake provider's observed behavior. This is not proof that a real model is immune to prompt injection; real outputs still need validation and review.

The structured proposal has **exactly** six fields: `transaction_id`, `decision` (`keep`/`change`), `group` (13 groups or `unmatched`), `status` (`business`/`personal`), `confidence` in `[0,1]`, and a nonblank reason of at most 160 characters. Extra fields, source edits, unknown values, wrong IDs, and contradictory keep/change proposals are rejected. The model cannot authoritatively set revenue or change amount/date; code uses the unchanged Plaid signed amount and the shared `revenue-v1` function. A valid `change` produces a flag at **any** confidence and changes only the illustrative reviewed label. A valid `keep` produces no flag. Neither automatically changes a live offer.

Refusal, incomplete output, malformed/invalid output, and provider outage are distinct **degraded** outcomes that visibly retain the legacy label. A `keep` is never used as a failure fallback. `ReviewOutcome` retains the legacy label, raw provider reply, validated proposal if any, final semantic labels, code-derived revenue, confidence/reason through the proposal, status, usage, and error. Ticket 05 will add provider access, cache, budget and strict offline-miss behavior; Ticket 06 will add credit math. Run `uv run --group dev pytest tests/test_reviewer.py` for fake-provider and adversarial tests. No live model call is made by Ticket 04.
