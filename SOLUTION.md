# Fundo transaction-label reviewer — solution (final measurements pending)

> **Submission status:** implementation and unit tests are in place, but the paid 2,000-transaction cache, no-key replay audit and full-cohort quality report are **not complete**. Do not treat the development-pilot numbers below as final accuracy. This file will be updated after the final run. All data is synthetic; no result is a live funding decision.

## Approach and boundary

I built the challenge's in-scope path as a Python batch CLI, not a production service. A fixed-seed, Plaid-shaped input contains 10 synthetic businesses, 90 declared coverage days and 2,000 posted transactions; scenario-intent truth is a **separate** file. A separate 61-day fixture tests incomplete coverage. Plaid Transactions' sign convention is preserved: **negative = inflow; positive = outflow**. Input validation requires USD cents, account ownership and declared account coverage, excludes pending/out-of-window records, and never infers a zero-NSF history from missing fee transactions. The fixture generator, hashes and scenario inventory are in [`docs/SYNTHETIC_DATA.md`](docs/SYNTHETIC_DATA.md).

The deliberately imperfect, versioned keyword engine implements all 13 Fundo groups, explicit precedence, personal markers and matched-rule trace. Its `square` collision, punctuation misses and noisy names create reviewable errors rather than a secretly tuned baseline. Code, not the model, determines revenue eligibility: a **business inflow** whose winning group is not excluded. The reviewer sees a sanitized transaction plus this *existing* label/rule trace. Counterparty text is JSON-serialized, treated as untrusted data, and the model has no tools. The model may propose only `keep`/`change`, group, business/personal, confidence and a ≤160-character reason. Code validates the exact ID/schema/semantics; it does not let the model edit amounts, dates, revenue, credit features or offer. Every valid `change` becomes a flag and is applied only to an **illustrative reviewed counterfactual**, not to a real decision. Invalid/refused/outage responses visibly retain legacy with degraded status, never a fake `keep`. Confidence is self-reported, not calibrated. Prompt-injection wording is tested as data, but that does not prove model immunity.

For online calls I chose `gpt-6-luna` provisionally because it supports the Responses API and structured output at the published standard short-context prices of **$0.10/M input and $0.50/M output tokens** ([official model page](https://developers.openai.com/api/docs/models/gpt-6-luna), checked 2026-10-09). The local account imposes **10 RPM / 50 RPD**, so requests contain up to 80 independent transactions, require one validated answer per ID, pace calls, and stop on the daily limit. A proposed fallback, `gpt-5.6-luna`, has a separately configured standard-price guard (**$0.20/M input, $1.20/M output**), but its first paid pilot returned **`credit_balance_exhausted`**: the current API project has no credits, so neither model can yet finish the cohort. This is an external blocker, not a quality result for the fallback. Cache keys hash all reviewer-visible normalized evidence, legacy label/rules and model/prompt/schema/flag versions; ground truth is absent. Offline mode never loads an API key or provider and fails on a missing/corrupt cache entry. Online mode uses validated hits first. The append-only spend ledger reserves a conservative upper bound **before** calls and caps cumulative commitments at **$8**, below Fundo's **$10** maximum; unresolved calls remain reserved. See [`docs/EXECUTION.md`](docs/EXECUTION.md).

## Evidence and limits

**Measured on synthetic development pilot, not held out:** a weaker v1 structured approach rejected **5/20** responses for invented groups/overlong reasons. A v2 batch of 20 yielded 10 changes, 10 keeps and **three false changes** against authored intent. The revised v3 prompt made 7 changes, 13 keeps and zero false changes on the **same tuned 20 cases**; group/status agreement was **19/20** versus **12/20** for legacy. That comparison is useful for choosing a provisional prompt, not a generalization claim. Early 40×50 batch attempts also exposed whole-batch parse fragility and 10 RPM/50 RPD limits; the provider schema was relaxed only for reason/confidence so strict per-item application validation remains intact. The final 25×80 run is pending, as is held-out analysis for `biz_09`/`biz_10`. I will not claim full-cohort improvement before `reports/evaluation/quality_report.json` exists.

**Current usage accounting, to be updated after final run:** 55 settled provider calls reported **64,707 input / 23,738 output tokens**. At the cited standard prices this is **$0.0183397 usage-derived estimated cost**, *not* an invoice or verified billed charge. The ledger also has 15 unresolved reservations from failed/interrupted attempts; counting them at their pre-call upper bounds gives **$0.1454506 committed exposure** so far. The preflight maximum for a remaining 25×80 full cohort is **$0.2873897** for `gpt-6-luna` or **$0.6547794** for `gpt-5.6-luna` under their respective published standard-price assumptions. These are **estimates, not spend**; the final ledger, provider usage and any actual billing receipt available will be reported separately. I will not relabel an estimate as exact cash spent.

**Simulated, not measured reviewer accuracy:** [`reports/evaluation/sensitivity_report.json`](reports/evaluation/sensitivity_report.json) starts from independent scenario-intent truth. Seed `20261009` samples 40/100/200 valid alternative labels, exactly 2%/5%/10% of 2,000 accepted transactions; every ID, error type and amount is recorded. Those alternatives are authored for 1,033 cases, so the pool is biased toward missed revenue and is **not** a production error distribution. Separate targeted cases show the directional stakes: one high-dollar false-revenue label inflates eligible revenue by **$28,743.36** and illustrative offer by **$11,497.34**; one missed-revenue label reduces both by **$18,000.00** and **$7,200.00**. A plausible false `Active advance` repayment on a **$1,985.34** capital-equipment debit lowers the offer by **$441.19**; missing a **$639.23** real repayment raises it by **$142.05**. At NSF labels **5 → 6**, the illustrative offer falls to zero; **6 → 5** removes that cutoff. Floors and cutoffs can make an otherwise high-impact label have zero marginal offer effect. The final reviewer quality report must add actual false flags on hard negatives, concrete wrong labels, per-business signed/absolute AMR errors, and legacy/reviewed/truth feature and offer tables; those are **not yet measured on the full paid run**.

The shared `credit-features-v1` function uses the same accepted transactions and coverage for all three label sets. Deposits include *all* inflows, while eligible revenue is code-derived; AMR is eligible revenue × `30 / observed_common_days`. NSF/overdraft are label counts, not verified incidents; high-risk debit share uses all debits as denominator; other-funder daily payments use positive business `Active advance` debits only. The supplied offer rule is `1.2 × AMR − 20 × daily payments`, zero only when `NSF_count > 5`. Our explicit V1 choices are a nonnegative floor and final-only half-up cent rounding. Null ratios, numerators, denominators, raw terms and coverage warnings are retained in [`docs/CREDIT_POLICY.md`](docs/CREDIT_POLICY.md) and `credit_report.json`. A false revenue label tends to **overstate** AMR/offer, while a false repayment label tends to **understate** the offer; their dollar effects differ because the formula multiplies AMR by 1.2 but daily payments by 20, and because an NSF cutoff may override both.

## Two credit-judgment answers

**Zero NSF fees at a no-fee bank:** The model would observe a zero *fee-label count*, not evidence of zero failed payments. If that bank does not post an NSF charge, the feature is structurally censored and could make the account appear less risky than a fee-charging bank with the same payment behavior. I would carry bank/fee observability and coverage flags beside the count, use available returned-payment/ACH signals with provenance, and compare outcomes by bank before using zero as a favorable signal. Unknown failures must remain unknown, not fabricated transactions.

**61 days into a 90-day-trained model:** Normalizing AMR to 30 days does not restore the missing 29 days of NSF opportunities, seasonality, debit distributions or confidence in revenue stability. A model trained on 90-day counts may misread a low 61-day count as low risk. The input contract computes the **intersection of declared account coverage** and exposes observed days; production should monitor that distribution, flag 61-day cases as out-of-training-window, and route them to a separately validated short-history policy or human review rather than silently substituting a normalized 90-day vector.

## Proposed production design — not deployed

Run the versioned reviewer **in shadow** beside the frozen keyword engine for at least four weeks on a consented, underwriter-annotated sample across businesses, banks and coverage lengths. Preserve both labels and show flags/reasons without changing a live funding decision. Compare per-business **absolute AMR dollar error**, decision-impacting false changes, hard-negative false-flag rate, offer deltas and underwriter burden against the same baseline. My *proposed* promotion gate—not Fundo policy—is ≥20% lower aggregate absolute AMR error, ≤5% false flags among annotated hard negatives, zero unmitigated high-impact false corrections, and underwriting/risk sign-off. Even after such a gate, a decision-changing flag requires a human to approve it; no automatic live offer change follows merely from model confidence.

Version and monitor coverage/pending exclusions, label distributions, revenue/AMR, NSF/overdraft, high-risk debit share, funder payments and offer distributions by bank, business cohort and input/rules/model/prompt/feature version. Compare every keyword or classifier update against a frozen canary corpus; alert and block promotion on unexplained shifts. A retrained model or keyword fix changes **upstream risk-model inputs**, so monitoring only final approval rate is too late. Track invalid/refused/provider-failed rates and cache misses as reliability metrics distinct from model agreement.

For a historical decline, retain an immutable access-controlled transaction/input snapshot and hash; accepted/excluded records and account coverage; old legacy labels and matched-rule trace; raw/validated reviewer outputs, cache/provider status, and all input/rules/model/prompt/schema/flag/feature/offer versions; derived features, illustrative offer, the **actual human decision** and underwriter action. A later keyword fix creates a new version and a new replay, never rewrites the old record. Underwriters inspect source evidence, accept/reject/correct flags with a reason, and their feedback enters a versioned, quality-checked evaluation set before any rule/prompt change. An override is not automatically ground truth. Access control, retention and consent would be specified before real data use.

## Scope, tools, reproducibility

No real customer data, Plaid API/Sandbox connection, web UI, database, production service, risk-model retraining, agent framework or live funding automation was built; none is required for this synthetic take-home demonstration. The challenge suggests 6–8 hours, but actual effort has not been timed reliably and will not be represented as meeting that estimate. Tools used: Plaid and OpenAI official documentation for data/model assumptions; Python 3.12, `uv`, Pydantic, OpenAI Python SDK, pytest and Git; and **OpenAI Codex as an AI coding/research assistant**. AI-generated code and interpretations were checked through source review, deterministic fixture hashes, fake-provider and boundary tests, measured pilot inspection, spend-ledger accounting, and (still pending) clean-checkout/no-key final replay. The key remaining gate is a complete, committed model-response cache followed by the exact offline audit and full synthetic quality report.
